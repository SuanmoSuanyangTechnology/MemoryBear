# Quality Check — 需求开发后质量检查工作流

## 适用场景

- 一个需求（feature 或 bugfix）开发完成、即将合并或自测前
- 已有改动想进行二次复盘
- 想评估某段代码在「1000 人并发 × 50 次访问」场景下的健壮性

## 输入要求（缺失时主动询问）

- **改动范围**：spec 名 / 目录 / 文件列表 / git diff 范围（如 `git diff main...HEAD`）任选其一
- **需求摘要**：1～3 句话说明此次需求的目标
- **可选**：性能预算（目标 P95 延迟、QPS）、关键 SLO

## 执行步骤（按顺序完成）

### Step 0：盘点改动

1. 读取相关 spec（若提供）：`requirements.md` / `design.md` / `tasks.md`
2. 用 `git diff` / `git log` 或 `grep_search` 锁定本次改动的文件清单
3. 列出受影响的层（controller / service / repository / pipeline / worker / DB schema / 前端）
4. 没有明确改动列表时，先反问确认范围，避免误检查

### Step 1：代码逻辑简洁性检查

聚焦「能不能更短、更直、更少分支」：

- 是否存在重复逻辑（同一段处理在多处出现，未抽公共方法）
- 是否有可被标准库 / 已有 utils 替代的手写实现
- 嵌套层级是否过深（> 3 层 if/for 视为可疑）
- 是否有「写了但没用到」的参数、返回值、字段
- 控制流是否能用 early-return / guard clause 简化
- Celery / Pipeline / Step 的职责是否单一，有没有跨层调用

输出：列出可简化点，每项给出**位置 + 当前写法摘要 + 建议写法**。

### Step 2：代码可读性检查

聚焦「下一个看代码的人能不能 30 秒看懂」：

- 命名：函数 / 变量是否符合 PEP 8（snake_case / PascalCase / UPPER_SNAKE_CASE），名字是否表意
- 函数长度：单函数超 50 行视为可疑，超 100 行必须拆
- 注释 / docstring：公共函数是否有 docstring（Google 风格），复杂逻辑是否有「为什么」级别的注释（不是「做什么」）
- 类型注解：函数参数和返回值是否有类型注解（PEP 484）
- 魔法数字 / 字符串：是否抽为常量或枚举（如 `BizCode`）
- 异常处理：是否使用项目自定义异常体系（`BusinessException` / `ValidationException`）而非裸 `Exception`
- 日志：是否经过 `sensitive_filter`，关键路径是否有 INFO 级别日志，错误是否有 stack trace
- 前端：组件是否过大（> 300 行需拆），hooks 命名是否 `use*`，i18n 字段是否齐全（en / zh）

输出：每项标注 `严重 / 一般 / 提示` 三档。

### Step 3：代码边界性检查

聚焦「输入越界、空值、并发、失败时会发生什么」：

- **空值与默认值**：`None` / `[]` / `{}` / 空字符串是否被正确处理
- **数值边界**：0、负数、超大值（如分页 size 超过 1 万）
- **字符串边界**：空、超长、含特殊字符 / Unicode / SQL 关键字 / Cypher 关键字
- **集合边界**：空集合、单元素、超大集合（触发分批的阈值是否合理）
- **时间边界**：时区、夏令时、跨天 / 跨月 / 跨年、未来时间、Unix epoch
- **外部依赖失败**：DB / Neo4j / Redis / ES / LLM 超时、连接拒绝、部分失败时的回退路径
- **事务一致性**：跨库写入（PG + Neo4j + ES）是否有补偿 / 幂等机制
- **幂等性**：Celery 任务、写入流水线重试是否安全
- **权限边界**：JWT / API Key 是否覆盖；`/api` 与 `/v1` 两套鉴权是否走对
- **并发写入**：同一资源被多个 worker / 请求同时改动时的锁或乐观控制

输出：以「输入维度 × 路径」表格列出未覆盖的边界。

### Step 4：跨模块影响面分析

聚焦「这次改动还会牵动谁」：

1. **静态依赖**：用 `grep_search` / `readCode` 找出本次改动的符号被哪些文件引用
2. **运行时依赖**：
   - DB schema 改动 → Alembic migration 是否同步、是否需要回填
   - Neo4j 索引 / 节点结构改动 → `repositories/neo4j/` 中是否有对应索引创建逻辑
   - Pydantic schema 改动 → 前端 API 类型 / Zustand store 是否同步
   - Celery 任务签名改动 → `celery_app.py` 路由配置是否同步、旧任务是否还会进队
   - 配置项（`core/config.py`）改动 → `env.example` / 部署文档是否同步
3. **被影响的上下游模块**（MemoryBear 项目特别关注）：
   - `MemoryService` → `WritePipeline` → `ExtractionStep` 链路
   - 写入与读取流水线共享的存储层
   - 去重 / 情绪 / 元数据 Celery 旁路任务
   - Reflection / Forgetting / Clustering 三大引擎对存储模型的依赖
4. **前端联动**：API 形状变更是否需要刷 axios client、views、i18n、ECharts/X6 图表
5. **测试影响面**：哪些已有 pytest 用例需要更新，是否有遗漏的回归点

输出：影响清单 + 每项的「需要同步改 / 需关注 / 已隔离」三档判定。

### Step 5：高并发与高数据量评估（1000 人 × 50 次）

> 目标场景：1000 并发用户，每人 50 次请求，总量 ≈ 5 万次请求；做**定性分析 + 关键路径指标估算**。

#### 5.1 入口层（FastAPI）
- 是否有 `async def`，路由内是否存在阻塞调用阻塞 event loop
- uvicorn worker 数与 CPU 核数是否匹配
- 全局锁 / 单例 / 缓存的并发安全性

#### 5.2 数据库层
- **PostgreSQL**：连接池大小（`pool_size` / `max_overflow`）；N+1 查询；索引；全表扫描；长事务
- **Neo4j**：批量写入；MERGE 索引；同节点并发写入锁竞争；大图读取上限
- **Redis**：大 key（元素 > 1 万）；热 key；Lua 脚本执行时长；Celery broker 队列堆积
- **Elasticsearch**：查询 size 上限；deep pagination；批量写入；向量检索参数对延迟影响

#### 5.3 任务队列（Celery）
- 任务路由：是否进了正确的队列
- 幂等性：失败重试是否产生重复数据
- 长任务（> 60s）是否阻塞队列；`soft_time_limit` / `time_limit` 是否合理
- 旁路 fire-and-forget 任务高峰期堆积估算

#### 5.4 LLM / 外部依赖
- 批处理 / 缓存（embedding 复用）
- 单次 LLM 调用 P95 延迟
- 限流 / 重试 / 熔断策略

#### 5.5 前端
- 虚拟滚动 / 分页
- 高频接口节流 / 防抖 / SWR 缓存
- `useEffect` 请求风暴

#### 5.6 输出格式
每个子项给出：**现状** / **风险** / **建议**。

### Step 6：生成报告

将上述检查整合为 Markdown 报告，写入：

```
.kiro/quality-reports/{feature-name}-{YYYYMMDD}.md
```

- `{feature-name}`：本次需求对应的 spec 名（kebab-case）；若无 spec，根据需求摘要生成
- `{YYYYMMDD}`：当天日期；同天多次追加 `-v2` / `-v3`

## 严重程度判定标准

- **❌ 阻断**：会引发线上故障、数据损坏、鉴权绕过、SQL/Cypher 注入、明显的 N+1 + 大数据量、连接池必然耗尽
- **⚠️ 一般**：可读性差、可简化、边界覆盖不全、性能可优化但短期不致命
- **ℹ️ 提示**：风格、注释、命名、可选增强

## 行为约束

- **只读优先**：默认只做静态分析与报告，不修改业务代码；如需修复，先报告再询问
- **基于事实**：所有结论必须给出文件路径 + 行号 / 函数名；不臆测；无法确认时明确写「未验证」
- **遵循项目规范**：参照 `.kiro/steering/tech.md`（PEP 8、命名、类型注解）和 `.kiro/steering/structure.md`（分层架构）
- **避免泄漏敏感信息**：报告中不出现 `.env` / 凭证 / token 实际值
- **结尾给链接**：报告生成后，回复中给出报告路径，方便用户点开查看
